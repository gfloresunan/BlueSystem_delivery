# ADR-011.3 — SUBMIT MERCHANT APPLICATION FORENSIC E2E AUDIT

**System:** BlueSystem Delivery Enterprise — Merchant Onboarding Portal  
**Domain:** Enterprise Identity & Access Management (EIAM v2.2)  
**Date:** 2026-08-08  
**Audit Target:** `submitMerchantApplication` Cloud Function & Client Fallback Pipeline  
**Status:** AUDIT COMPLETE — READY FOR CONTROLLED IMPLEMENTATION  

---

## 1. Executive Summary

During production testing of the Merchant Onboarding Portal (`https://bluesystem-7c9af-apply.web.app/`), application submission failed at the network layer with a browser CORS policy error blocking fetch calls to `https://us-central1-bluesystem-7c9af.cloudfunctions.net/submitMerchantApplication`. Following this error, the client executed a fallback mechanism (`[EIAM Portal] Callable function no disponible, guardando directamente en Firestore`) and presented a "¡Solicitud Enviada con Éxito!" confirmation to the user.

A forensic audit of code, network preflights, and Firebase deployment logs reveals that the callable function `submitMerchantApplication` was originally not deployed to production. In Google Cloud Functions, requests to non-existent function endpoints return HTTP 404 without `Access-Control-Allow-Origin` headers, which browsers intercept as CORS failures before evaluating HTTP status codes. The client SDK caught this missing endpoint error as `FirebaseError: internal`, triggering a client-side direct Firestore write fallback.

## 10. Function Responsibilities

The server-side callable `submitMerchantApplication` executes the following responsibilities:
1. **Mandatory Field Validation:** Validates existence of `businessName`, `email`, `phone`, and `ruc`.
2. **Email Syntax Validation:** Enforces regex pattern `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`.
3. **Duplicate Prevention Check:** Queries `/merchant_applications` where `email == cleanEmail` and `status in ['PENDING', 'UNDER_REVIEW', 'APPROVED', 'ONBOARDING']`. Throws `functions.https.HttpsError('already-exists')` if found.
4. **Document Structuring:** Creates a new document reference with server-generated ID `db.collection("merchant_applications").doc()`.
5. **Server Timestamping:** Applies `FieldValue.serverTimestamp()` for `createdAt` and `updatedAt`.
6. **Audit & Logging:** Writes structured logs via `Logger.info(...)`.
7. **Controlled Response:** Returns explicit payload `{ success: true, applicationId: appRef.id, message: "..." }`.

---

## 11. Fallback Responsibilities

The direct client-side Firestore write fallback (`submitMerchantApplicationDirect` in earlier portal builds) executes:
1. **Direct Collection Write:** Invokes Firestore client SDK `addDoc(collection(db, 'merchant_applications'), payload)`.
2. **Client Validation Only:** Relies entirely on frontend form checks.
3. **Bypasses Server Checks:** Bypasses active email duplicate verification, regex enforcement, and server-side log generation.
4. **Security Alignment:** Writes document with `status: 'PENDING'`, which is permitted under `firestore.rules` for unauthenticated users.

---

## 12. EIAM Impact

- **Provisioning Flow:** EIAM account provisioning and claim assignment do NOT occur directly inside `submitMerchantApplication`. Instead, provisioning is triggered asynchronously by the Firestore background trigger `onMerchantApplicationApproved` (`functions/src/triggers/merchantApplications.ts`), which fires on document `UPDATE` when `status` transitions to `APPROVED`.
- **Impact Assessment:** Applications created via fallback still contain all required fields (`email`, `businessName`, `ruc`, `location`, `documents`). When an admin approves the application in the Governance Center, `onMerchantApplicationApproved` will fire normally. Therefore, downstream EIAM account provisioning is NOT broken by fallback document creation.

---

## 13. Governance Impact

- **Duplicate Control Failure:** Bypassing the backend callable prevents duplicate detection against existing active applications. Governance administrators may receive multiple identical application records for the same merchant.
- **Intake Triage Integrity:** Lack of server-side audit logs means governance intake metrics cannot verify whether an application originated via validated callable logic or unvalidated direct database insert.

---

## 14. Security Impact

- **Firestore Security Rules Analysis (`firestore.rules` lines 296-311):**
  ```firestore
  match /merchant_applications/{appId} {
    allow create: if request.resource.data.status == 'PENDING'
                  && request.resource.data.email is string
                  && request.resource.data.businessName is string;
    allow read: if isPlatformAdmin() || (isAuthenticated() && request.auth.token.email == resource.data.email);
    allow update: if isPlatformAdmin();
    allow delete: if false;
  }
  ```
- **Permission Check:** Public users can create documents ONLY with `status == 'PENDING'`. Public users CANNOT set status to `APPROVED`, update existing documents, or grant EIAM permissions.
- **Risk Assessment:** No authorization escalation risk exists. However, the collection is vulnerable to spam/duplicate document creation if the callable function is not strictly enforced.

## 16. Idempotency

- **Callable Function:** Idempotent. Attempting to submit twice with the same email throws `functions.https.HttpsError('already-exists')`.
- **Direct Fallback:** Non-idempotent. Multiple submissions create multiple distinct documents in `/merchant_applications` with identical merchant details.

---

## 17. False Success Risk

- **Mechanism:** When the Cloud Function call fails (e.g. 404/CORS or Network error), catching the error and falling back to a direct Firestore write followed by displaying "¡Solicitud Enviada con Éxito!" presents a **False Success**.
- **Architectural Risk:** The UI signals complete system acceptance to the user even though critical backend validations (duplicate check, server audit) were completely bypassed. If the direct write also fails (or if Firestore rules change), the user receives conflicting state feedback.

---

## 18. Root Cause

1. **Deployment Omission:** The callable function `submitMerchantApplication` was authored in `functions/src/callables/merchant.ts` and exported in `functions/src/index.ts`, but was not deployed to GCP Cloud Functions prior to initial portal testing.
2. **GCP CORS Masking on 404:** Non-existent endpoints on Google Cloud Functions return HTTP 404 without CORS origin headers. Web browsers block missing CORS origin headers before processing HTTP status, producing a misleading CORS policy error in the client console.
3. **Over-Permissive Client Fallback:** Client portal code handled callable invocation errors by falling back directly to Firestore `addDoc`, masking infrastructure errors and bypassing backend validation.

---

## 19. Recommended Fix

1. **Deploy all Merchant Callables:** Deploy `submitMerchantApplication`, `getMerchantApplicationStatus`, `updateMerchantWizardStep`, and `completeMerchantWizard` to `us-central1`.
2. **Harden Client Function Invocation (`merchant-onboarding-portal/src/firebase.ts`):**
   - Eliminate direct Firestore write fallbacks in production.
   - Properly map callable errors (`already-exists`, `invalid-argument`, `permission-denied`) to user-friendly UI messages.
   - For network/connectivity errors, prompt the user to retry rather than performing unvalidated direct database writes.
