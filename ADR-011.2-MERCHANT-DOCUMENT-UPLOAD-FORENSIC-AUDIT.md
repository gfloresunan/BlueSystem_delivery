# ADR-011.2 — Merchant Document Upload E2E Forensic Audit

**Sprint:** 18.2 / Upload Forensic Audit
**Date:** 2026-08-09
**Status:** ROOT CAUSE CONFIRMED — READY FOR IMPLEMENTATION

---

## 1. Executive Summary

After a deep static code analysis and production bundle inspection, **three critical bugs** were identified in `Step3Documents.tsx` that cause the document upload flow to silently fail from the user's perspective, even though the Firebase Storage layer itself is correctly configured and functional.

The bugs are:
1. **Critical — Stale Closure (BUG A):** The `onProgress` callback inside `handleFileUpload` closes over `formData.documentFiles` at the moment the upload starts, not at the moment the progress fires. As files are added (or re-renders happen), this stale reference tries to `.map()` over the *original empty array*, so the progress update call to `updateForm` overwrites the list with an empty (or prior-state) array — effectively **erasing the newly added document from the UI list** mid-upload.

2. **Critical — Stale Closure on Upload Complete (BUG B):** The `updateForm` call after `uploadDocumentFile` resolves (the `completed` update block) also uses `formData.documentFiles.map(...)` — again, the *stale value from when the handler was created*. At this point `formData.documentFiles` is the **pre-upload snapshot** (empty array), so mapping over it produces an empty array as well. The document disappears from the UI list on completion.

3. **Medium — `accept` Attribute vs. Validation List Mismatch (BUG C):** The `<input>` element uses `accept=".pdf,.png,.jpg,.jpeg"` (file-extension format). Some browsers/OS combinations serve these files with MIME types like `image/jpg` (rather than `image/jpeg`). The MIME validation list includes `image/jpg`, so this is not a blocker, but it is a defensive inconsistency.

**Net visible result:** The user selects a file → the file name briefly appears in the list for one render frame → both progress updates and the completion update overwrite `documentFiles` back to an empty array → the item visually disappears → no upload indicator, no success, no error. The actual Firebase Storage upload *does* start in the background (confirmed by bundle analysis), but the UI never reflects it.

9. The list collapses back to empty. The upload icon/progress disappears.
10. The user sees a blank dropzone again. Nothing appears to have happened.

## 6. Root Cause

### BUG A — Stale Closure in `onProgress` (CRITICAL)

**Location:** `Step3Documents.tsx` lines 57–63

```tsx
// BUG: formData.documentFiles is captured at the time handleFileUpload runs,
// not at the time onProgress fires. After the initial state update (line 49),
// the *real* state has changed, but the closure holds the old empty array.
(progress) => {
  updateForm({
    documentFiles: formData.documentFiles.map((doc) =>    // ← STALE: []
      doc.name === file.name ? { ...doc, progress } : doc
    ),
  });
}
```

**Consequence:** `formData.documentFiles` is `[]` at closure-creation time (initial mount). After `updateForm({ documentFiles: updatedList })` runs, React schedules a re-render — but the `onProgress` callback was already captured with the old value. When progress fires, it maps over `[]`, produces `[]`, and calls `updateForm({ documentFiles: [] })`, erasing the new entry.

---

### BUG B — Stale Closure on Upload Complete (CRITICAL)

**Location:** `Step3Documents.tsx` lines 67–81

```tsx
// BUG: Same stale closure problem. At the time this code runs,
// formData.documentFiles is still the captured empty array, not
// the updated array with the uploading document.
updateForm({
  documentFiles: formData.documentFiles.map((doc) =>     // ← STALE: []
    doc.name === file.name
      ? { ...doc, progress: 100, status: 'completed', ... }
      : doc
  ),
});
```

**Consequence:** Even if BUG A didn't wipe the list, this call would wipe it on completion.

---

### BUG C — `accept` vs. MIME check inconsistency (MEDIUM)

The `<input accept=".pdf,.png,.jpg,.jpeg">` triggers OS-level file filtering. The actual MIME type the browser reports can vary (especially `image/jpg` vs `image/jpeg`). This is handled in the MIME list but should be standardized using MIME types directly in `accept`.

## 7. Evidence

### 7.1 Code Evidence — Stale Closure

In `Step3Documents.tsx`:

```tsx
// Line 48-49: updatedList is built and sent via updateForm
const updatedList = [...formData.documentFiles, newDoc];
updateForm({ documentFiles: updatedList });   // React state updates asynchronously

// Line 57-63: onProgress uses formData.documentFiles (the PRE-update value)
(progress) => {
  updateForm({
    documentFiles: formData.documentFiles.map(   // formData here = old stale closure
      (doc) => doc.name === file.name ? { ...doc, progress } : doc
    ),
  });
}
```

`formData` is a prop received from `OnboardingPage`. It is **captured once** when `handleFileUpload` is called. After `updateForm` propagates and the parent re-renders, `Step3Documents` receives a new `formData` prop — but the old `handleFileUpload` invocation is still executing with its **closed-over old `formData`**.

## 15. Recommended Fix

### Fix A — Replace stale `formData.documentFiles` references with functional state updaters

The root of the problem is using `formData.documentFiles` (a closed-over prop value) inside async callbacks. The correct React pattern is to use the **functional form of the state setter** to guarantee access to the latest state. Since `updateForm` is a prop function, it needs to be redesigned to accept functional updaters, OR the component needs to store `documentFiles` in local state (not just read from props).

**Option 1 — Use functional updater in `updateForm` (requires OnboardingPage.tsx change):**

This is the cleanest fix. Modify `updateForm` in `OnboardingPage.tsx` to support functional updaters:

```tsx
// OnboardingPage.tsx — NO change needed; it already uses functional updater:
const updateForm = (data: Partial<MerchantFormData>) => {
  setFormData((prev) => ({ ...prev, ...data }));
};
// But the PROBLEM is that `data` is computed using the stale `formData`.
```

The real fix is in `Step3Documents.tsx`: use a **local useState** for `documentFiles`, synchronized from props on mount only, and call `updateForm` with the final result.

**Option 2 (Recommended) — Use local ref for the `updatedList` and reference it in callbacks:**

Use a `useRef` to always have the latest documentFiles available inside the async closure:

```tsx
// Inside Step3Documents
const docFilesRef = useRef(formData.documentFiles);
useEffect(() => {
  docFilesRef.current = formData.documentFiles;
}, [formData.documentFiles]);
```

Then replace all stale `formData.documentFiles.map(...)` calls in the handler with `docFilesRef.current.map(...)`.

**Option 3 (Simpler, no ref) — Track the file list locally during the upload:**

Build the update payload manually using the `updatedList` variable that was already computed at the start of the handler, rather than re-reading from `formData`:

```tsx
// Before the upload starts, capture a local variable:
const updatedList = [...formData.documentFiles, newDoc];
updateForm({ documentFiles: updatedList });

// Use updatedList in callbacks (not formData.documentFiles):
(progress) => {
  updateForm({
    documentFiles: updatedList.map((doc) =>
      doc.name === file.name ? { ...doc, progress } : doc
    ),
  });
}

// On complete:
updateForm({
  documentFiles: updatedList.map((doc) =>
    doc.name === file.name
      ? { ...doc, progress: 100, status: 'completed', storagePath: uploadResult.storagePath, ... }
      : doc
  ),
});
```

**Option 3 is the minimal, isolated fix** aligned with the project's "minimum change" rule.

### Fix B — Align `accept` attribute with MIME types

```tsx
// Replace:
accept=".pdf,.png,.jpg,.jpeg"

// With:
accept="image/jpeg,image/png,application/pdf"
```
