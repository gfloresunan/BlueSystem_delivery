## 1. Gatekeeper Architecture & Rule Evaluation

In `flutter_client/lib/core/gatekeeper/gatekeeper.dart`:
- `GatekeeperEngine.canAccessModule({required GatekeeperContext context, required String moduleKey})` enforces an 8-step sequential evaluation chain:
  1. **Structural Context Validation:** Checks non-empty `uid`, `membershipId`, and `tenantId`. Rejects with `AccessDecisionReason.contextInvalid` if malformed.
  2. **Platform Admin Bypass:** SuperAdmin, Admin, and Auditor roles receive access across all platform management surfaces.
  3. **Subscription Presence:** If `context.subscription == null`, immediately rejects with `AccessDecisionReason.subscriptionMissing`.
  4. **Tenant Isolation Check:** If `sub.tenantId != context.tenantId`, immediately rejects with `AccessDecisionReason.tenantMismatch`.
  5. **Subscription Status Check:** Suspended, cancelled, archived, past due, or inactive statuses trigger immediate denial (`subscriptionInactive` / `subscriptionExpired`).
  6. **Temporal Boundary Checks:** Enforces `startDate <= now` and `endDate >= now`.
  7. **Entitlement Feature Check:** Verifies module key against subscription tier features (`sub.isFeatureEnabled`).
  8. **Role-Module Mapping:** Verifies user role has necessary authorization for the specific module (e.g. `KDS` requires cook/manager/owner/cashier).

## 2. Fail-Closed Invariant

- **Default Behavior:** **DENY (Bloqueo por defecto)**.
- **No Bypass:** There are no client-side switches to disable the Gatekeeper engine.
- **Double Shield:** Even if UI elements are tampered with locally, backend Firestore Rules and Cloud Functions enforce identical entitlement gates server-side.
